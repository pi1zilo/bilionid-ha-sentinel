# 🛡️ BilioniD HA Sentinel

**Отказоустойчивый Telegram-бот мониторинга и базового управления инфраструктурой на базе двух VPS.**

Проект обеспечивает непрерывный мониторинг состояния серверов, телеметрии Beszel, статуса мониторов Uptime Kuma и Docker-контейнеров с автоматическим переключением между основным сервером (**Main / Primary**) и резервным сервером (**Backup / Standby**) по защищенной приватной сети **Tailscale**.

## 1. Архитектура системы

Инфраструктура строится на базе двух независимых VPS узлов, объединенных приватной виртуальной сетью Tailscale:

| Параметр | Main (Основной сервер) | Backup (Резервный сервер) |
|---|---|---|
| **Назначение** | Основной рабочий узел | Резервный узел (горячий standby) |
| **Tailscale IP (пример)** | `100.64.0.1` | `100.64.0.2` |
| **Роль HA** | **PRIMARY** (активный бот) | **STANDBY** (горячий резерв) |
| **HA Port** | **29010** (Tailscale private) | **29010** (Tailscale private) |

> [!IMPORTANT]
> Для служебного межсерверного взаимодействия HA выбран легковесный порт **29010**, изолированный внутри виртуальной сети Tailscale и защищенный pre-shared ключом в заголовке `X-HA-Secret`.

## 2. Ключевые возможности

- 🖥 **Мониторинг серверов:** CPU, RAM (исп./всего/%), Диск (исп./всего/свободно/%), Load Average (1m, 5m, 15m), Uptime в удобном виде (например, `5 дней 2 часа`), температура оборудования (если поддерживается).
- 📊 **Отказоустойчивая интеграция с Beszel:** автоматическое чтение метрик с Primary Beszel Hub с мгновенным переключением на Backup Hub при сбое. Локальный сборщик `psutil` как резерв при недоступности обоих Hub.
- ⏱ **Интеграция с Uptime Kuma:** чтение мониторов, времени отклика и инцидентов. Полностью опциональна и не блокирует работу бота при недоступности.
- 🐳 **Мониторинг Docker-контейнеров:** отображение состояния контейнеров на обоих VPS через защищенный federated HA-endpoint.
- 🔄 **Автоматический High Availability:**
  - В штатном режиме опрос Telegram API (`getUpdates`) выполняется **только** на Main.
  - При аварии Main резервный узел Backup через 30 секунд принимает управление на себя.
  - При восстановлении Main управление автоматически возвращается на основной сервер через 30 секунд непрерывной стабильности.
  - Строгая защита от конфликта одновременного polling (Telegram 409 Conflict Fencing).
- 🚨 **Оповещения в Telegram:** мгновенные уведомления об авариях, переключениях роли, восстановлении узлов и инцидентах.
- 🔒 **Строгая безопасность:** доступ разрешен только указанному `TELEGRAM_ADMIN_USER_ID`, маскирование секретов в логах, rate limiting, работа в контейнере без root-прав.

## 3. Как работает High Availability (HA)

В двухсерверной конфигурации отсутствует третий свидетель (кворумный witness). Для предотвращения Split-Brain реализована многоуровневая система защиты:

1. **HA Supervisor:** независимый легковесный фоновый процесс, работающий непрерывно на обоих серверах вне зависимости от Telegram polling.
2. **Heartbeat & Multi-vector Probe (каждые 5 сек):** Backup проверяет Main по трем направлениям:
   - HTTP-запрос к HA-endpoint `http://<MAIN_IP>:29010/health`.
   - TCP socket к порту 29010.
   - HTTP-проверка Main Beszel Hub `http://<MAIN_IP>:29001/api/health`.
   Если хотя бы один сервис отвечает — Main признается живым.
3. **Failover Threshold (30 секунд):** переключение происходит только при 6 последовательных неудачных проверках (30 секунд непрерывной недоступности).
4. **Outbound Internet Egress Check:** перед захватом управления Backup проверяет доступность внешнего Telegram API (`api.telegram.org`). Если резервный сервер сам изолирован от интернета, он **не запускает polling**, избегая ложных аварий.
5. **Telegram API Fencing (409 Conflict):** Telegram API физически запрещает два одновременных `getUpdates`. Если Backup ловит ошибку 409, он мгновенно отключает polling, защищая кластер от Split-Brain.
6. **Recovery Yield (Failback):** после восстановления Main Backup ждет 30 секунд непрерывной стабильности, после чего плавно останавливает polling (`dp.stop_polling()`) и передает лидерство Main.

Подробный анализ рисков и архитектурные диаграммы приведены в [ARCHITECTURE.md](ARCHITECTURE.md).

## 4. Быстрый старт: Инструкция по развёртыванию

Развёртывание полностью автоматизировано с помощью интерактивного скрипта `deploy.sh`.

### Предварительные требования:
- Linux (Ubuntu / Debian) на обоих серверах.
- Установленные Docker и Docker Compose v2.
- Настроенный Tailscale (ноды доступны друг другу по приватным IP).
- Токен Telegram-бота от `@BotFather`.
- Telegram Chat ID для уведомлений и ваш Telegram User ID.

---

### Шаг 1: Развёртывание на Main (PRIMARY)

1. Подключитесь по SSH к **Main**:
   ```bash
   ssh user@<MAIN_TAILSCALE_IP>
   ```

2. Склонируйте репозиторий и перейдите в директорию проекта:
   ```bash
   git clone git@github.com:pi1zilo/bilionid-ha-sentinel.git
   cd bilionid-ha-sentinel
   ```

3. Запустите интерактивный установщик:
   ```bash
   bash deploy.sh
   ```

4. Ответьте на вопросы мастера:
   - **Роль сервера:** выберите `1) MAIN / PRIMARY` (по умолчанию).
   - **Tailscale IP текущего узла:** подтвердите или введите IP (скрипт определяет автоматически).
   - **Tailscale IP парного сервера:** укажите IP резервного сервера (Backup).
   - **Порт HA Supervisor:** `29010` (по умолчанию).
   - **HA_SECRET_KEY:** сгенерируйте случайный ключ или введите свой (скопируйте его, он понадобится на Backup!).
   - **Telegram Bot Token:** введите ваш токен (установщик проверит его через Telegram API).
   - **Telegram Chat ID:** укажите ID чата/группы для алертов.
   - **Telegram Admin User ID:** укажите ваш персональный Telegram ID.
   - **Параметры Beszel Hub & Uptime Kuma:** подтвердите URL или настройте порты.

5. Установщик сгенерирует `.env`, защитит его правами `chmod 600`, соберет Docker-образ, запустит контейнер и проверит healthcheck.

6. Проверьте статус:
   ```bash
   ./deploy.sh --status
   ```
   В Telegram-чате напишите `/start` — бот ответит главным меню!

---

### Шаг 2: Развёртывание на Backup (STANDBY)

1. Подключитесь по SSH к **Backup**:
   ```bash
   ssh user@<BACKUP_TAILSCALE_IP>
   ```

2. Склонируйте репозиторий на резервный сервер и перейдите в него:
   ```bash
   git clone git@github.com:pi1zilo/bilionid-ha-sentinel.git
   cd bilionid-ha-sentinel
   ```

3. Запустите интерактивный установщик:
   ```bash
   bash deploy.sh
   ```

4. Ответьте на вопросы мастера:
   - **Роль сервера:** выберите `2) BACKUP / STANDBY`.
   - **Tailscale IP текущего узла:** подтвердите или укажите IP Backup сервера.
   - **Tailscale IP парного сервера:** укажите IP Main сервера.
   - **Порт HA Supervisor:** `29010`.
   - **HA_SECRET_KEY:** вставьте **тот же самый секретный ключ**, который был указан на Main!
   - **Telegram Bot Token:** тот же самый токен бота.
   - **Telegram Chat ID & Admin User ID:** те же значения, что на Main.

5. Установщик запустит контейнер Backup в режиме **STANDBY**. Telegram polling на Backup будет отключен, пока Main здоров.

## 5. Проверка работоспособности и симуляция HA

Для безопасной проверки отказоустойчивости **без реального отключения production-серверов** предусмотрен скрипт симуляции:

```bash
# Запуск с сервера Main или Backup
python3 scripts/simulate_ha_test.py http://<MAIN_IP>:29010 http://<BACKUP_IP>:29010 <ВАШ_HA_SECRET_KEY>
```

Скрипт проверит:
1. Доступность обоих HA-endpoints по Tailscale.
2. Соблюдение инварианта единственного лидера (активен ровно 1 polling-процесс).
3. Защиту от неавторизованного доступа (HTTP 401 при отсутствии ключа).
4. Прохождение тестового пакета Heartbeat.

### Проверка в Telegram:
- Отправьте боту команду `/ha`: вы увидите статус обоих узлов, время непрерывной доступности, состояние lease и связность.

## 6. Инструкция восстановления после аварии

### Сценарий 1: Авария на Main (Failover)
1. Основной сервер `Main` становится недоступен (сбой сети, перезагрузка, зависание).
2. Через 30 секунд Supervisor на `Backup` фиксирует потерю связи и проверяет доступ в интернет.
3. `Backup` активирует polling и присылает сообщение в Telegram:
   > 🚨 **АВАРИЯ ИНФРАСТРУКТУРЫ: FAILOVER**  
   > Основной сервер недоступен более 30 сек.  
   > Резервный экземпляр принял управление на себя.
4. Все команды бота продолжают работать через резервный сервер.

### Сценарий 2: Восстановление Main (Failback)
1. Вы восстанавливаете работоспособность основного сервера или он загружается после перезагрузки.
2. `Backup` видит появление `Main` и начинает отсчет 30 секунд стабильности.
3. По истечении 30 секунд `Backup` останавливает свой polling, освобождает lease и возвращает роль `STANDBY`.
4. `Main` возобновляет опрос Telegram и отправляет уведомление:
   > ✅ **ВОССТАНОВЛЕНИЕ: FAILBACK TO PRIMARY**  
   > Основной сервер полностью восстановился и стабилен.  
   > Управление возвращено на Primary.

### Сценарий 3: Ручное принудительное переключение
Если вам требуется срочно переключить активный узел вручную (например, для регламентных работ):
1. Отправьте боту команду `/ha`.
2. Нажмите кнопку **⚡ Ручное переключение**.
3. Подтвердите действие: узел переключит состояние с фиксацией события в журнале аудита.

## 7. Команды и интерфейс Telegram-бота

### Список команд:
- `/start` — Главное меню с навигационными inline-кнопками.
- `/help` — Подробная справка по всем командам.
- `/status` — Сводка по всей инфраструктуре (оба сервера, мониторы, кластер).
- `/servers` — Список обоих серверов с компактными метриками.
- `/server main` — Полная карточка основного сервера.
- `/server backup` — Полная карточка резервного сервера.
- `/containers` — Список всех Docker-контейнеров на обоих VPS.
- `/ha` — Диагностика HA-кластера, состояние lease, heartbeat и ручное переключение.
- `/beszel` — Статус обоих Beszel Hubs (Main и Backup).
- `/uptime` — Список и статусы мониторов Uptime Kuma.
- `/alerts` — Журнал последних аварий и переключений.
- `/refresh` — Принудительное обновление кэша данных.

## 9. Безопасность и защита данных

- **Авторизация:** доступ к боту жестко ограничен переменной `TELEGRAM_ADMIN_USER_ID`. Посторонние пользователи получают отказ в доступе.
- **Защита от утечек:** токен бота, пароли и секретный ключ `HA_SECRET_KEY` маскируются в логах и никогда не выводятся в Telegram.
- **Изоляция сети:** межсерверное взаимодействие происходит исключительно по приватным IP Tailscale (`100.x.x.x`). Порт `29010` защищен секретным ключом.
- **Ограничение прав Docker:** контейнер запускается от имени пользователя `appuser` (UID 1000) с запретом повышения привилегий (`no-new-privileges`). Сокет Docker монтируется строго в режиме **read-only** (`:ro`).
- **Read-Only безопасность:** бот не выполняет произвольные команды shell.

Подробный отчет по безопасности доступен в [SECURITY.md](SECURITY.md).

## 10. Удаление проекта

Для полного и безопасного удаления проекта используйте скрипт:

```bash
bash uninstall.sh
```

Скрипт:
1. Запросит подтверждение.
2. Остановит и удалит контейнер `bilionid-ha-sentinel` через `docker compose down`.
3. Предложит удалить локальный Docker-образ.
4. Предложит создать резервную копию базы данных и `.env`.
5. Полностью очистит директорию проекта.

> [!NOTE]
> Удаление затрагивает **исключительно** контейнеры и данные `bilionid-ha-sentinel`. Все остальные сервисы сервера (Beszel, Uptime Kuma, Portainer, базы данных) остаются в полной сохранности.
